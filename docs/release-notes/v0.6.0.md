# secdat v0.6.0 Release Notes

## Highlights

- `set --generate` creates a random secret directly in the selected key.  It
  requires an explicit length and character-set policy, and can require every
  selected character class to appear.
- `save` writes a passphrase-protected portable secret bundle from the current
  `ls` view or from repeated `--key` selections.  New bundle v2 files keep
  bundle-local value objects separate from logical base-name labels without
  serializing source domain/store, inheritance, masks, attributes, UUIDs, or
  wrapped keys.
- `load` imports into exactly the selected `--dir` and `--store` destination.
  It defaults to `--conflict=reject`; `overwrite` and `skip` are explicit
  alternatives.  Bundle framing, duplicate names, and all conflicts are
  checked before writing an entry.  Loading a shared v2 object to a v1 store
  is rejected unless `--allow-link-split` explicitly permits separate values.

## Compatibility and security

- Existing v1 key/value bundles remain readable.
- Bundle v2 authenticates its envelope header as AES-GCM additional
  authenticated data, so header tampering is rejected.
- A bundle is portable data, not an origin snapshot: it does not recreate its
  source domain/store hierarchy or source metadata.

## SDK and bindings

- The C ABI is unchanged from v0.5.0.  Python, Rust, and Node binding package
  versions track the core release at `0.6.0`; the Rust binding requires
  `libsecdat >= 0.6.0` through `pkg-config`.

## Validation

- The release candidate is checked with the FUSE-enabled package-shape matrix,
  installed-consumer checks, and the portable-bundle acceptance matrix.
